# SOLID — п'ять принципів на п'яти прикладах

Кожен принцип — окрема тека з парою `before.py` / `after.py`. Обидва файли запускаються
і показують проблему та її вирішення на екрані:

```bash
cd module01/09_solid
poetry run python -m solid_ex.s_single_responsibility.before
poetry run python -m solid_ex.s_single_responsibility.after
```

## S — Single Responsibility (принцип єдиної відповідальності)

**Один модуль — одна причина для змін.**

У `before.py` метод `OrderReport.show_table()` робить три роботи одночасно: рахує суму,
форматує таблицю і друкує. Тому коли знадобився JSON, метод скопіювали — і копія
`show_json()` розійшлася з оригіналом: у таблиці є гуртова знижка, у JSON її забули.
Два звіти показують різні суми за одні й ті самі замовлення.

В `after.py` кожна робота — окрема функція: `line_total()` і `order_total()` рахують,
`render_table()` та `render_json()` форматують, `send_to_console()` виводить. Обидва
формати читають одну й ту саму `line_total()`, тому розійтися вже не можуть.

**Питання для перевірки:** чи можу я отримати суму, не друкуючи звіт?

## O — Open/Closed (принцип відкритості/закритості)

**Нову поведінку додають новим кодом, а не редагуванням старого.**

У `before.py` тип знижки визначає ланцюжок `if/elif` у `final_price()` — і другий такий
самий ланцюжок у `receipt_line()`. Кожен новий тип клієнта означає правку обох функцій,
і рано чи пізно хтось поправить одну та забуде іншу.

В `after.py` кожна знижка — окремий клас з інтерфейсом `Discount` (`apply()` + `label`).
`PercentDiscount` покриває всі відсоткові знижки одним класом, `BulkDiscount` має власну
логіку з порогом. Нова знижка — це новий клас; `receipt_line()` і наявні знижки не
змінюються взагалі (тест `test_o_discounts.py` створює нову знижку прямо в тесті).

**Питання для перевірки:** скільки наявних файлів доведеться редагувати, щоб додати
наступну знижку?

## L — Liskov Substitution (принцип підстановки Лісков)

**Підклас має виконувати кожну обіцянку базового класу.**

`before.py` ламає це двома способами, як у реальному коді:

- `ReadOnlyStorage(Storage)` кидає `PermissionError` із `save()` — метод оголошений,
  але відмовляється працювати. Загальна функція `backup()`, написана для `Storage`,
  падає посеред циклу.
- `CompressedStorage(Storage)` тихіше і тому гірше: `save()` стискає дані, а `read()`
  успадкований — тож повертає стиснуті байти замість збереженого тексту. Нічого не
  падає, просто `verify()` показує `corrupted`.

В `after.py` ієрархія збудована за можливостями: `ReadableStorage` вміє лише читати,
`WritableStorage` додає `save()`, а `CompressedStorage` перевизначає **і** `save()`,
**і** `read()` — контракт «прочитаєш те, що зберіг» виконується, хоча внутрішнє
представлення інше. Сховище тільки для читання — це просто `ReadableStorage`: воно
більше не обіцяє `save()`, і анотація `list[WritableStorage]` у `backup()` не пускає
його туди на рівні тайп-чекера.

**Питання для перевірки:** чи можу я передати підклас у код, написаний для базового
класу, і піти, не перевіряючи?

## I — Interface Segregation (принцип розділення інтерфейсів)

**Клієнт не повинен залежати від методів, яких не викликає.**

У `before.py` один товстий інтерфейс `MultiFunctionDevice` вимагає `print`, `scan` і
`fax` від кожного пристрою. `CheapPrinter` вміє лише друкувати, тому змушений заглушити
два методи через `NotImplementedError` — а кожна така заглушка це, по суті, порушення L:
оголошена поведінка, якої немає. `scan_documents()` падає на середині пачки документів.

В `after.py` інтерфейс розрізаний на ролі: `Printer`, `Scanner`, `Fax`. `OfficeStation`
успадковує всі три, `CheapPrinter` — лише `Printer`, і жодної заглушки. Функція
`scanners_in()` відбирає з парку техніки тільки те, що справді вміє сканувати, через
`isinstance(device, Scanner)`.

**Питання для перевірки:** скільки методів потрібно найменшому корисному тестовому
дублеру?

## D — Dependency Inversion (принцип інверсії залежностей)

**Високорівнева логіка і низькорівневі деталі залежать від абстракції, а не одне від одного.**

У `before.py` `OrderService` сам створює собі `PostgresOrders` і `SmtpClient` в
`__init__`. Наслідок: сервіс неможливо запустити без бази й SMTP, неможливо протестувати
без мережі, а заміна пошти на Telegram — це правка бізнес-логіки.

В `after.py` сервіс отримує обидві залежності через конструктор і знає лише абстракції
`OrderRepo` та `Notifier`. Продакшн збирається як
`OrderService(PostgresOrders(), EmailNotifier())`, локальна розробка — як
`OrderService(InMemoryOrders(), TelegramNotifier())`, а тест підставляє `FakeNotifier`
на чотири рядки і перевіряє точний текст повідомлення (`test_d_order_service.py`).
Інверсія — це напрямок стрілки: раніше сервіс залежав від SMTP, тепер і сервіс, і
SMTP-клієнт залежать від `Notifier`.

**Питання для перевірки:** чи можу я створити цей клас із висмикнутим мережевим кабелем?

## Як L та I пов'язані

Класичне порушення L — підклас, що кидає `NotImplementedError` — майже завжди наслідок
завширокого інтерфейсу: у підкласа просто не було чесного способу його реалізувати.
Розділення інтерфейсу (I) — це ліки від такого порушення L. Порівняйте
`l_liskov/before.py` та `i_interface_segregation/after.py` — це одна й та сама розмова
з двох боків.

## Тести

```bash
poetry run pytest -v
```

| Файл | Що доводить |
| --- | --- |
| `test_o_discounts.py` | нова знижка визначена прямо в тесті й працює без жодної правки наявного коду |
| `test_l_storage.py` | у `before` підкласи ламають код, написаний для базового класу; в `after` контракт читання виконується, а read-only сховище не обіцяє `save()` |
| `test_d_order_service.py` | фейкові репозиторій і нотифікатор перевіряють точні повідомлення — без бази і без SMTP |
