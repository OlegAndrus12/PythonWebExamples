# Singleton — один екземпляр на процес

```bash
cd module01/08_patterns/singleton
python3 main.py                # версія на модулі (2 файли)
python3 settings_minimal.py    # мінімальна реалізація на __new__
python3 settings_classic.py    # повна реалізація на __new__
```

Лише стандартна бібліотека, Python 3.12+.

| Файл | Що в ньому |
| --- | --- |
| [`settings.py`](settings.py) | сам приклад: звичайний клас `Settings` + кешована `get_settings()` |
| [`main.py`](main.py) | демонстрація: спільний об'єкт, змінний стан, тестовий шов |
| [`settings_minimal.py`](settings_minimal.py) | 8 рядків `__new__` без деталей; усі три пастки видні відразу |
| [`settings_classic.py`](settings_classic.py) | той самий конфіг класичним патерном — `__new__` плюс блокування, прапорець, весь инвентар |

Три останні файли — один і той самий конфіг трьома способами:
- **minimal** — 8 рядків, хоча б так видно проблему;
- **classic** — повна версія з усіма фіксами і захистами;
- **settings.py** — той самий результат на модулі, три строчки коду на доступ.

## Що це таке

**Singleton** — породжувальний (creational) патерн: клас, у якого може існувати
рівно один екземпляр, плюс глобальна точка доступу до нього.

Формулювання з книжки GoF складається з двох частин, і друга важливіша за першу.
"Один екземпляр" — це обмеження. "Глобальна точка доступу" — це те, заради чого
патерн зазвичай і беруть: щоб не тягнути об'єкт через п'ять рівнів викликів.

## Яку проблему вирішує

Є речі, які дорого або небезпечно створювати двічі:

- **конфігурація** — читання `.env`, валідація, перетворення типів; та й розбіжні
  копії конфігу в різних частинах застосунку — це джерело багів, які не
  відтворюються;
- **пул з'єднань до БД** — кожен екземпляр відкриває свої з'єднання, а Postgres
  має `max_connections`;
- **клієнт кешу / брокера** — Redis-клієнт тримає сокет;
- **логер** — два логери з однією назвою дублюють кожен рядок у файлі;
- **реєстр** — карта "ім'я → обробник", яка має бути одна, інакше половина
  обробників невидима.

Спільне в усіх випадках: створення має побічний ефект (сокет, файл, гроші, час),
і другий екземпляр не просто зайвий — він шкідливий.

## Класична реалізація і чому вона погана

```python
class Settings:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance.debug = False
        return cls._instance
```

Працює. Далі — рахунок, який приходить пізніше (усе це видно на екрані, якщо
запустити сусідній [`../01_singleton.py`](../01_singleton.py)):

1. **Тести течуть один в одний.** Тест A виставив `debug = True` — тест B це
   бачить. Скинути нема як: конструктор перехоплено, а `_instance` доводиться
   чистити руками з приватного атрибута.
2. **Перевірка не атомарна.** Між `if cls._instance is None` і присвоєнням може
   втрутитися інший потік. Вісім потоків спокійно створюють вісім "сінглтонів".
   Лікується блокуванням — тобто ще одним шаром коду.
3. **Об'єкт не копіюється.** `copy.deepcopy(a) is a`. Іноді це саме те, чого
   хотіли, але частіше — сюрприз.
4. **Нічого не підмінити.** Немає точки, куди вставити фейковий об'єкт для
   тесту чи інший конфіг для staging.
5. **Ініціалізація стає впорядкованою.** `__init__` викликається на *кожному*
   `Settings()`, а не лише на першому, — і мовчки перезаписує стан. Класична
   пастка цієї реалізації.
6. **Спадкування ламається.** `_instance` живе на базовому класі; підклас або
   отримає екземпляр батька, або доведеться писати словник по класах.

Головне ж: у Python цей код розв'язує задачу, якої немає. Патерн придумали для
C++ та Java, де немає модулів як об'єктів першого класу.

## Як це роблять у Python

**Тіло модуля виконується один раз на процес.** Перший `import settings` виконує
файл, наступні дістають готовий об'єкт зі `sys.modules`. Модуль — це вже
сінглтон, до того ж потокобезпечний: імпорт захищений блокуванням інтерпретатора.

Звідси два способи, і обидва в цій теці:

```python
# 1. Об'єкт на рівні модуля — найпростіше
settings = Settings.from_env()

# 2. Кешована функція — те саме, але ліниво і з кнопкою скидання
@lru_cache(maxsize=1)
def get_settings() -> Settings:
    return Settings.from_env()
```

Різниця між ними одна, але суттєва: варіант 1 виконується під час імпорту, тому
відсутня змінна середовища валить застосунок на першому `import`, ще до того, як
щось встигне залогуватися. Варіант 2 відкладає це до першого звернення — і дає
`get_settings.cache_clear()`, той самий шов, якого класичному сінглтону бракує.

Зверніть увагу на те, чого в [`settings.py`](settings.py) **немає**: клас
`Settings` — найзвичайніший, без `__new__`, без метакласу, без декоратора. Він
навіть не знає, що він сінглтон, і не заважає створити другий екземпляр —
`Settings.from_env() is get_settings()` дає `False`. За "рівно один" відповідає
модуль, а не клас. Саме через це клас лишається тестованим: у тесті ви створюєте
скільки завгодно окремих `Settings`, а застосунок бере той один, що з кешу.

Ще одна свідома деталь — `Settings.from_env(env)`: конструювання відокремлене
від кешування. Тест може зібрати конфіг зі звичайного словника, не чіпаючи ні
кеш, ні `os.environ`.

Зворотний бік звичайного класу — екземпляр змінний, і `main.py` це чесно
показує: `get_settings().debug = True` спрацьовує, і наступний виклик віддає вже
зіпсований конфіг. Це той самий глобальний змінний стан, за який лають
`__new__`-версію. Різниця лише в тому, що тут є `cache_clear()`, щоб його
скинути. Якщо хочеться заборони, а не дисципліни, — `@dataclass(frozen=True)`
закриває питання одним рядком (`__slots__` у прикладі ловить лише друкарські
помилки в іменах атрибутів, не мутацію).

## Що показує `main.py`

```
1. Невалідне оточення падає при першому зверненні, а не при імпорті
2. Оточення читається один раз; get_settings() is get_settings() -> True
3. sys.modules тримає один модуль; Settings.from_env() is get_settings() -> False
4. get_settings().debug = True -> мутація проходить, конфіг зіпсовано
5. cache_clear() + Settings.from_env(fake_env) -> тестовий шов
```

## Як це тестувати

```python
import pytest
from settings import get_settings


@pytest.fixture(autouse=True)
def clear_settings_cache():
    get_settings.cache_clear()
    yield
    get_settings.cache_clear()


def test_debug_off_requires_secret(monkeypatch):
    monkeypatch.delenv("SECRET_KEY", raising=False)
    monkeypatch.setenv("DEBUG", "false")
    with pytest.raises(RuntimeError):
        get_settings()
```

`autouse`-фікстура з `cache_clear()` — стандартний прийом. Саме його неможливо
написати для сінглтона на `__new__`, не лізучи в приватні атрибути класу.

## Коли доречно, а коли ні

**Доречно:** конфігурація, пули з'єднань, клієнти зовнішніх сервісів, реєстри
обробників — тобто дороге створення + очевидно спільний ресурс.

**Не доречно:** усе, що має стан, який змінюється під час роботи. "Кошик
покупця", "поточний користувач", "лічильник запитів" сінглтонами бути не можуть —
це не один об'єкт на процес, це один об'єкт на запит.

Два обмеження, про які згадують надто пізно:

- **Сінглтон — один на процес, не на застосунок.** `gunicorn -w 4` — це чотири
  незалежні екземпляри. Лічильник у сінглтоні порахує приблизно чверть. Спільний
  стан між воркерами живе в Redis чи БД, а не в пам'яті процесу.
- **Сінглтон — це прихована залежність.** Функція, яка всередині кличе
  `get_settings()`, у сигнатурі про це не каже. Для конфігу з цим миряться; для
  всього іншого чесніше передати залежність аргументом — див.
  [`../../09_solid/`](../../09_solid/), принцип Dependency Inversion.

## Підсумок

Патерн Singleton у Python — це майже завжди відповідь на запитання, яке вже
розв'язала система модулів. Пишіть звичайний клас і одну функцію доступу на
рівні модуля; `@lru_cache(maxsize=1)` додає лінивість і `cache_clear()`. `__new__`,
метакласи й декоратори класів залишіть для співбесід — там про них питають.
