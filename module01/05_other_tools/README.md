# 05 — Інші інструменти: pyenv і pipx

У цій теці **немає коду** — тільки цей довідник. Попередні три папки навчили керувати залежностями
**всередині** проєкту. Тут — два інструменти, які працюють **зовні**: один керує версіями самого
Python, другий — утилітами командного рядка.

Розділення обов'язків, яке варто тримати в голові з самого початку:

| Рівень                        | Питання                                                         | Інструмент                   |
| ----------------------------------- | ---------------------------------------------------------------------- | -------------------------------------- |
| Інтерпретатор          | «яка версія Python?»                                        | **pyenv** (або `uv python`) |
| Глобальні утиліти   | «чим лінтувати й форматувати будь-що?» | **pipx** (або `uv tool`)    |
| Залежності проєкту | «що імпортує цей код?»                               | pip / Poetry / uv                      |

Три різні задачі. Плутанина між ними — джерело майже всіх проблем на кшталт «встановив, а команда не
знаходиться».

---

# Частина 1. pyenv

## Яку проблему вирішує

У системі стоїть один Python — той, що приніс macOS, Debian чи Homebrew. Проблеми починаються, коли:

- застосунок на роботі вимагає 3.11, а новий пет-проєкт хочеться писати на 3.14;
- треба перевірити, чи бібліотека працює на 3.12 **і** на 3.13;
- системний Python оновився разом з ОС — і всі ваші venv зламалися;
- ви зіпсували системний інтерпретатор, а на нього спирається сама операційна система.

**venv тут не допоможе.** Віртуальне середовище ізолює *пакети*, але створюється на базі вже наявного
інтерпретатора. Якщо в системі немає 3.13, `python -m venv` його не вигадає.

pyenv ставить будь-яку кількість версій Python поруч і дозволяє перемикати їх — глобально, для теки
або для одного запуску.

## Встановлення

**macOS:**

```bash
brew install pyenv
```

**Linux** (потрібні бібліотеки для збірки — pyenv **компілює** Python з вихідних кодів):

```bash
# Ubuntu / Debian
sudo apt update && sudo apt install -y \
  build-essential libssl-dev zlib1g-dev libbz2-dev libreadline-dev \
  libsqlite3-dev curl libncursesw5-dev xz-utils tk-dev libxml2-dev \
  libxmlsec1-dev libffi-dev liblzma-dev

curl -fsSL https://pyenv.run | bash
```

**Windows:** самого pyenv немає — є окремий порт
[pyenv-win](https://github.com/pyenv-win/pyenv-win). Або WSL, або одразу `uv`.

### Налаштування оболонки — крок, який усі пропускають

Без цього pyenv встановиться, але **нічого не перемикатиме**. Для zsh у `~/.zshrc`:

```bash
export PYENV_ROOT="$HOME/.pyenv"
[[ -d $PYENV_ROOT/bin ]] && export PATH="$PYENV_ROOT/bin:$PATH"
eval "$(pyenv init - zsh)"
```

Для bash — те саме в `~/.bashrc`, з `bash` замість `zsh`. Далі перезапустити термінал і перевірити:

```bash
pyenv --version        # pyenv 2.8.3
which python           # має вказувати на ~/.pyenv/shims/python
```

## Як воно працює: shims

Це єдина концепція, яку треба зрозуміти, і після неї всі дивні поведінки стають очевидними.

pyenv кладе в `PATH` **раніше за все інше** теку `~/.pyenv/shims/`. Там лежать не інтерпретатори, а
крихітні скрипти-посередники з іменами `python`, `pip`, `pytest` тощо. Коли ви набираєте `python`,
запускається shim; він дивиться, яка версія має діяти **тут і зараз**, і передає керування
справжньому бінарнику.

Порядок, у якому pyenv вирішує, «яка версія зараз»:

1. змінна оточення `PYENV_VERSION` (її ставить `pyenv shell`);
2. файл `.python-version` у поточній теці;
3. такий самий файл у батьківських теках, вгору до кореня;
4. `~/.pyenv/version` — глобальна версія (`pyenv global`).

Перше знайдене виграє. Перевірити, звідки саме взялася версія:

```bash
pyenv version           # 3.13.13 (set by /Users/me/project/.python-version)
pyenv version-origin    # шлях до файлу, який вирішив
pyenv which python      # повний шлях до справжнього бінарника
```

> **Наслідок, який усіх дивує:** після `pip install <щось-із-командою>` нова команда може не
> знайтися. Shim для неї ще не створено. Лікує `pyenv rehash` — вона перестворює shims. Сучасні
> версії роблять це автоматично, але коли команда «зникла», перевіряти треба саме це.

## Команди

```bash
pyenv install --list              # усі доступні версії (довгий список)
pyenv install --list | grep " 3.13"
pyenv install 3.13.13             # зібрати й поставити (кілька хвилин!)
pyenv install 3.13                # найсвіжіший патч цієї гілки
pyenv latest 3.13                 # яка версія вважається найсвіжішою
pyenv install --skip-existing 3.13.13

pyenv versions                    # що встановлено; * позначає активну
pyenv version                     # яка активна зараз і чому

pyenv global 3.13.13              # версія за замовчуванням для всієї системи
pyenv local 3.12.11               # для цієї теки — створює .python-version
pyenv shell 3.11.9                # тільки для цієї сесії терміналу
pyenv shell --unset

pyenv uninstall 3.11.9
pyenv which python                # шлях до справжнього бінарника
pyenv exec python -V              # запустити в обхід shim
pyenv rehash                      # перестворити shims
```

Усі команди й прапорці в цьому довіднику перевірені на **pyenv 2.8.3** і **pipx 1.16.6**. Повний
перелік — `pyenv commands` і `pipx --help`.

Дрібниця, яка стає в пригоді у скриптах: `pyenv install --list --bare` друкує голий список версій без
заголовків і відступів — саме те, що можна пропустити через `grep` чи `tail -1`.

### Файл `.python-version`

`pyenv local 3.13.13` створює в теці файл з одним рядком:

```
3.13.13
```

Його **комітять у git** — це декларація «цей проєкт очікує таку версію». Той самий файл читає й `uv`,
що робить його фактичним стандартом, а не особливістю pyenv.

## Кілька версій одночасно

```bash
pyenv global 3.13.13 3.12.11 3.11.9
```

Перша — та, яку дає `python`. Але тепер доступні й `python3.12`, і `python3.11`. Саме так запускають
`tox` чи `nox`, коли треба прогнати тести на кількох версіях.

## pyenv-virtualenv (необов'язковий плагін)

pyenv **не** керує віртуальними середовищами. Плагін додає таку можливість:

```bash
brew install pyenv-virtualenv       # + eval "$(pyenv virtualenv-init -)" у ~/.zshrc

pyenv virtualenv 3.13.13 myproject
pyenv local myproject               # тека автоматично активує це середовище
pyenv virtualenvs
pyenv uninstall myproject
```

Зручно, але з Poetry чи uv не потрібне — вони роблять venv самі.

## Типові граблі

| Симптом                                                       | Причина                                                                                                                                |
| -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `pyenv: command not found`                                         | не додано`eval "$(pyenv init -)"` у конфіг оболонки                                                                  |
| `python` досі системний                               | не перезапущено термінал, або shims не перші в`$PATH`                                                      |
| Команда після`pip install` не знаходиться | потрібен`pyenv rehash`                                                                                                              |
| `ModuleNotFoundError: No module named '_ssl'`                      | не було системних бібліотек під час компіляції — доставити й`pyenv install` заново |
| `BUILD FAILED`                                                     | те саме: бракує заголовкових файлів (`libssl-dev` тощо)                                                   |
| Встановлення триває вічно                     | так і має бути: pyenv**компілює** Python. Кілька хвилин — норма                                    |

# Частина 2. pipx

## Яку проблему вирішує

Є два принципово різні типи Python-пакетів:

- **бібліотеки**, які ви імпортуєте (`requests`, `flask`) — їм місце у venv проєкту;
- **застосунки**, які ви запускаєте (`black`, `ruff`, `httpie`, `poetry`, `pre-commit`) — вони не
  мають жодного стосунку до коду проєкту.

Три способи поставити другий тип, і два з них погані:

```bash
pip install black                 # ❌ у venv проєкту: у кожному проєкті окремо, і воно в requirements
sudo pip install black            # ❌ у системний Python: ламає залежності ОС
pipx install black                # ✅
```

pipx створює для **кожної утиліти окреме віртуальне середовище**, а її команди виставляє в
`~/.local/bin`. Утиліти не бачать одна одну, конфлікт версій між ними неможливий, а видалення —
це видалення однієї теки.

> Головна відмінність від `pip install --user`: там усі утиліти ділять один простір імен пакетів.
> Дві утиліти, яким потрібні несумісні версії `click`, просто зламають одна одну.

## Встановлення

```bash
# macOS
brew install pipx
pipx ensurepath

# Linux
sudo apt install pipx     # або: python3 -m pip install --user pipx
pipx ensurepath

# будь-де, якщо є uv
uv tool install pipx
```

`pipx ensurepath` дописує `~/.local/bin` у `PATH` — без цього встановлені команди не знайдуться.
Після неї треба перезапустити термінал.

```bash
pipx --version           # 1.16.6
pipx environment         # де саме pipx тримає venv і бінарники
```

## Команди

```bash
pipx install ruff                 # поставити утиліту
pipx install "poetry==2.4.1"      # конкретну версію
pipx install --python 3.12 mypy   # на конкретному інтерпретаторі

pipx list                         # що встановлено, з якими командами
pipx list --short

pipx upgrade ruff
pipx upgrade-all
pipx reinstall-all                # після оновлення Python — перезібрати всі середовища

pipx uninstall ruff
pipx uninstall-all

pipx run cowsay "hi"              # запустити, НЕ встановлюючи
pipx run --spec httpie http GET example.com

pipx inject poetry poetry-plugin-export   # доставити пакет в середовище утиліти
pipx runpip poetry list                   # запустити pip усередині її середовища

pipx ensurepath                   # полагодити PATH
pipx list --include-injected      # показати й доінжектовані пакети
pipx list --outdated              # для чого є новіші версії
pipx health                       # перевірити, чи все ціле
pipx environment                  # де саме pipx тримає venv і бінарники
```

Три команди, які рятують, коли «щось поламалося»:

| Команда         | Коли                                                                                                                   |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `pipx health`        | загальна діагностика — перше, що варто запустити                                  |
| `pipx reinstall-all` | після оновлення Python: середовища вказують на зниклий інтерпретатор |
| `pipx repair`        | те саме, але точковим ремонтом, без перевстановлення                           |

### `pipx run` — найнедооціненіша команда

```bash
pipx run ruff check .
```

Завантажує `ruff` у окреме середовище й запускає — **не** додаючи його до встановлених утиліт.
У `pipx list` воно не з'явиться, і команди `ruff` у `PATH` не буде.

**Але «тимчасове» не означає «одноразове».** З довідки самого pipx:

> The environment will be cached and reused for up to 14 days.

Тобто перший запуск повільний, наступні — миттєві, а через два тижні середовище перебудується. На
диску воно лежить весь цей час:

```bash
pipx cache dir                      # ~/Library/Caches/pipx (macOS)
pipx cache purge                    # видалити всі закешовані середовища
pipx run --no-cache ruff check .    # не використовувати кеш
pipx run --refresh ruff check .     # перебудувати кеш примусово
```

Ідеально для утиліт «на один раз» і для CI. Прямий аналог — `uvx`, який поводиться так само: теж
кешує, а не видаляє (`uv cache dir`, `uv cache clean`, `uv cache prune`).

> Практичний висновок: якщо на ноутбуку раптом бракує місця, каталоги кешу pipx і uv — перше, куди
> варто зазирнути. Кеш uv на цій машині, наприклад, важить **2,4 ГБ**.

### `pipx inject` — плагіни для утиліт

Утиліта в ізольованому середовищі не бачить своїх плагінів, доки їх туди не покласти:

```bash
pipx install poetry
pipx inject poetry poetry-plugin-export
```

Саме так додають плагіни Poetry, коли він поставлений через pipx. Це та сама причина, через яку
`poetry export` не працює «з коробки» — про це в [`../03_poetry/`](../03_poetry/).

## Типові граблі

| Симптом                                                         | Причина                                                                                                               |
| ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Команда не знаходиться після`pipx install`  | не виконано`pipx ensurepath` або не перезапущено термінал                               |
| Утиліти зламалися після оновлення Python | середовища вказують на зниклий інтерпретатор →`pipx reinstall-all`                |
| Плагін «не бачиться»                                 | потрібен`pipx inject <утиліта> <плагін>`                                                              |
| `pipx install` для бібліотеки                           | помилка вибору: бібліотеки ставлять у проєкт, pipx — тільки для команд |

# Частина 3. Як усе поєднується

Типове робоче місце Python-розробника до появи uv:

```
pyenv          керує версіями інтерпретатора
  └── pipx     ставить утиліти, кожну в своє середовище
        └── poetry / pip   керують залежностями конкретного проєкту
```

Приклад повного налаштування з нуля:

```bash
# 1. інтерпретатори
brew install pyenv
pyenv install 3.13.13
pyenv global 3.13.13

# 2. утиліти
brew install pipx && pipx ensurepath
pipx install poetry
pipx install ruff
pipx install pre-commit

# 3. проєкт
cd myproject
pyenv local 3.13.13
poetry install
```

Зверніть увагу: `poetry` встановлений **через pipx**, а не через `pip install poetry` всередині
проєкту. Менеджер залежностей не може бути залежністю того, чим він керує.

# Частина 4. uv замість обох

`uv` (папка [`../04_uv/`](../04_uv/)) свідомо покриває обидві ці ролі:

| Задача                                        | pyenv / pipx           | uv                                               |
| --------------------------------------------------- | ---------------------- | ------------------------------------------------ |
| Поставити інтерпретатор       | `pyenv install 3.13` | `uv python install 3.13`                       |
| Перелік версій                         | `pyenv versions`     | `uv python list`                               |
| Зафіксувати версію для теки | `pyenv local 3.13`   | `.python-version` (той самий файл) |
| Поставити утиліту                   | `pipx install ruff`  | `uv tool install ruff`                         |
| Запустити без встановлення  | `pipx run ruff`      | `uvx ruff`                                     |
| Оновити всі утиліти                | `pipx upgrade-all`   | `uv tool upgrade --all`                        |
| Перелік утиліт                         | `pipx list`          | `uv tool list`                                 |

Швидкість відрізняється принципово: pyenv **компілює** Python з вихідних кодів (хвилини), uv
**завантажує** готові збірки (секунди).

```bash
uv python list      # видно і встановлені, і доступні для завантаження
```

### Коли pyenv і pipx усе ще потрібні

- **Потрібна збірка з нетиповими прапорцями** — з оптимізаціями, з іншою бібліотекою SSL. uv роздає
  готові збірки, pyenv компілює під вас.
- **Дуже старі версії Python** — 2.7, 3.6. Готових збірок для них немає.
- **Альтернативні реалізації** — PyPy, Jython, Miniconda: pyenv ставить і їх.
- **У команді вже налагоджений процес** на pyenv/pipx — переходити без причини не варто.
- **Корпоративне середовище**, де новий інструмент ще не пройшов погодження.

Для нового проєкту у 2026 році розумний вибір — просто `uv`. Але pyenv і pipx треба знати: ви
зустрінете їх у більшості наявних проєктів і в кожній другій інструкції з налаштування.

## Шпаргалка

```bash
# ── pyenv ──────────────────────────────────────────────
pyenv install --list | grep " 3.13"    # що доступно
pyenv install 3.13.13                  # поставити
pyenv versions                         # що є
pyenv global 3.13.13                   # за замовчуванням
pyenv local 3.12.11                    # для теки (створює .python-version)
pyenv shell 3.11.9                     # для сесії
pyenv version                          # яка активна і чому
pyenv which python                     # справжній шлях
pyenv rehash                           # команда «зникла»

# ── pipx ───────────────────────────────────────────────
pipx ensurepath                        # полагодити PATH
pipx install ruff                      # поставити утиліту
pipx run ruff check .                  # запустити без встановлення (кеш на 14 днів)
pipx cache purge                       # прибрати закешовані середовища
pipx list                              # що стоїть
pipx upgrade-all                       # оновити все
pipx inject poetry poetry-plugin-export # плагін для утиліти
pipx health                            # діагностика
pipx reinstall-all                     # після оновлення Python
pipx uninstall ruff

# ── uv як заміна обом ──────────────────────────────────
uv python install 3.13
uv python list
uv tool install ruff
uv tool upgrade --all
uvx ruff check .
```
