# 02 — pip і requirements.txt

**Проєкт: `statusboard`** — невеликий застосунок на Flask. Він по черзі «стукає» до кількох відомих
сайтів (Cloudflare, AWS, Instagram, GitHub, PyPI), заміряє час відповіді й показує таблицю станів.
Друга вкладка витягує список останніх інцидентів Cloudflare з їхнього публічного API.

Тема заняття — **не Flask**, а `pip` і `requirements.txt`. Застосунок навмисно маленький (~150 рядків
Python), щоб уся увага була на тому, **де живуть залежності** і **як їх відтворити на іншій машині**.

Той самий застосунок з’явиться ще двічі — у `03_poetry` та в папці про `uv`. Код залишиться тим самим,
змінюватиметься лише спосіб опису залежностей. Коли між трьома заняттями відрізняється тільки
інструмент, то саме інструмент і вивчається.

| Папка                 | Маніфест                     | Що з’являється                                                                  |
| -------------------------- | ------------------------------------ | -------------------------------------------------------------------------------------------- |
| **02 — pip** (ця) | `requirements.txt`                 | нічого — просто файли в теці                                          |
| 03 — Poetry               | `pyproject.toml` + `poetry.lock` | пакет, збірка wheel, lock-файл із хешами                              |
| 04 — uv                   | `pyproject.toml` + `uv.lock`     | той самий маніфест, інший резолвер, значно швидший |

Наскільки саме «значно» — не на слово: у [`../07_compare/`](../07_compare/) лежить скрипт, який міряє
всі три на тих самих залежностях, і графік із результатами.

## Як запустити

```bash
cd module01/02_pipenv

python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate

pip install -r requirements.txt
flask --app app run --debug
```

Відкрити [http://127.0.0.1:5000](http://127.0.0.1:5000).

П’ять сервісів мають бути зелені, шостий (`no-such-host.invalid`) — червоний. Він зламаний **навмисно**:
інакше, щоб побачити, як виглядає помилка, довелося б чекати справжньої аварії.

Щоб вийти з віртуального середовища — `deactivate`.

## Структура

| Файл                     | Роль                                                                                                            |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `app.py`                   | маршрути Flask — точка входу                                                                     |
| `checks.py`                | перевіряє один URL і заміряє час; імпортує`requests`, але **не** Flask |
| `services.py`              | читає й пише список сервісів у JSON                                                        |
| `services.json`            | сам список: назва → URL                                                                              |
| `incidents.py`             | тягне інциденти з API Cloudflare                                                                     |
| `templates/base.html`      | спільний каркас сторінки                                                                      |
| `templates/index.html`     | сторінка зі станом сервісів                                                                 |
| `templates/incidents.html` | сторінка з інцидентами                                                                          |
| `static/style.css`         | усі стилі                                                                                                   |
| `requirements.txt`         | дві залежності, які проєкт справді просить                                      |

Правило, за яким розкладено файли: **шар вебу нічого не рахує сам**. `app.py` лише викликає
`checks`, `services`, `incidents` і віддає результат у шаблон. Тому `checks.py` можна без змін
використати з cron-скрипта, з тесту або з Telegram-бота.

## Частина 1. Віртуальне середовище

Виконайте це **до** і **після** активації:

```bash
which python && which pip     # Windows: where python
```

До активації — системний Python. Після — `.venv/bin/python`. Активація не робить нічого магічного:
вона додає `.venv/bin` на початок `$PATH` і виставляє змінну `$VIRTUAL_ENV`. Це майже весь механізм.

Наслідок, заради якого все й робиться:

```bash
python -c "import sys; print(sys.prefix)"
python -c "import flask, pathlib; print(pathlib.Path(flask.__file__).parent)"
```

Flask лежить у `.venv/lib/python3.x/site-packages/`, а не в системному Python. Тому два проєкти на
одній машині можуть залежати від **несумісних версій** тієї самої бібліотеки й не заважати одне одному.

Якщо встановлювати без venv, `pip install flask` кладе пакет у системний інтерпретатор — і потім
неможливо оновити один проєкт, не зламавши інший. На свіжих macOS та Debian pip прямо відмовляється:

```
error: externally-managed-environment
```

Це не помилка, а повідомлення «зроби venv».

> **Головне:** venv можна будь-коли видалити й створити наново — там немає нічого цінного.
> Саме тому `.venv/` записаний у `.gitignore`, а `requirements.txt` — ні.

## Частина 2. Команди pip

```bash
pip list                    # що встановлено
pip show flask              # версія, залежності, шлях
pip show -f flask           # ...і всі файли, які пакет поклав на диск
pip list --outdated         # для чого є новіші версії
pip index versions flask    # усі доступні версії на PyPI
```

Зверніть увагу на рядок `Requires:` у `pip show flask` — `blinker`, `click`, `itsdangerous`,
`jinja2`, `markupsafe`, `werkzeug`. Ви попросили **один** пакет, а отримали **сім**. Тепер подивіться
з іншого боку: `pip show werkzeug` і рядок `Required-by:`.

### Довідник

| Команда                      | Що робить                                                                                               |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `python3 -m venv .venv`           | створити віртуальне середовище                                                      |
| `source .venv/bin/activate`       | активувати (Windows:`.venv\Scripts\activate`)                                                       |
| `deactivate`                      | вийти                                                                                                      |
| `pip install flask`               | встановити пакет                                                                                 |
| `pip install 'flask==3.1.0'`      | встановити конкретну версію                                                            |
| `pip install -r requirements.txt` | встановити все зі списку                                                                   |
| `pip install -U flask`            | оновити                                                                                                  |
| `pip uninstall flask`             | видалити (його залежності**залишаються**)                                |
| `pip freeze`                      | вивести повний список встановленого                                             |
| `pip check`                       | перевірити, чи не поламані залежності                                           |
| `pip cache purge`                 | очистити кеш wheel-ів                                                                              |
| `python -m pip ...`               | безпечна форма — гарантує, в який саме інтерпретатор ставимо |

Останній рядок варто зробити звичкою. Якщо в системі кілька Python, то `pip` — це той, який першим
трапився в `$PATH`, а `python -m pip` — однозначно той, який ви щойно запустили.

## Частина 3. Головне питання заняття — `requirements.txt`

Ви попросили два пакети. Подивіться, що встановилося:

```bash
pip list
```

Близько дванадцяти, бо в залежностей є свої залежності. Тепер згенеруйте файл автоматично:

```bash
pip freeze
```

```
blinker==1.9.0
certifi==2026.7.22
charset-normalizer==3.4.9
click==8.4.2
Flask==3.1.0
idna==3.18
itsdangerous==2.2.0
Jinja2==3.1.6
MarkupSafe==3.0.3
requests==2.32.3
urllib3==2.7.0
Werkzeug==3.1.8
```

Ваші номери будуть іншими — і це якраз суть: два рядки, які ви зафіксували, незмінні, а решту десять
вам видали такими, якими вони були на PyPI в день установки.

Порівняйте це з `requirements.txt`, у якому **два рядки**. Обидва файли сьогодні дають однакове
середовище. Але це не одне й те саме:

- **`pip freeze` — повний, але пласкій.** У ньому ніяк не видно, які два пакети ви обрали свідомо, а
  які приїхали причепом. Через рік на code review ніхто не скаже, чи `urllib3` імпортується у вашому
  коді, чи його притягнув `requests` — тому ніхто й не наважиться його прибрати.
- **Написаний руками файл виражає намір.** Два рядки — два рішення. Але транзитивні пакети в ньому
  не зафіксовані взагалі, тож `pip install -r requirements.txt` іншого дня дасть інший `urllib3`.

**Жоден із двох файлів не вміє робити обидві роботи одночасно.** Це не питання смаку, а брак
можливості. Саме цю дірку закривають Poetry та uv: маніфест із вашими прямими залежностями **плюс**
окремий lock-файл, який фіксує всі дванадцять разом із хешами.

### Види фіксації версій

| Запис       | Означає               | Коли                                                                               |
| ---------------- | ---------------------------- | -------------------------------------------------------------------------------------- |
| `Flask==3.1.0` | рівно ця версія | застосунки — потрібна відтворюваність                |
| `Flask>=3.1`   | ця або новіша     | бібліотеки — ви не знаєте обмежень користувача |
| `Flask~=3.1.0` | `>=3.1.0, <3.2.0`          | довіряєте патчам, але не мінорним версіям           |
| `Flask`        | будь-яка              | ніколи в тому, що деплоїте                                        |

Тут `==`, бо `statusboard` — застосунок.

## Частина 4. Чого pip **не** вміє

Кожен пункт — це тема наступних занять.

1. **Немає lock-файлу й немає хешів.** pip ставить те, що віддав PyPI. Якщо реліз підмінили — установка
   мовчки пройде успішно. `pip install --require-hashes` існує, але хеші треба вести вручну.
2. **Не розрізняє прямі й транзитивні залежності.** Про це вище — це найважливіший пункт.
3. **Немає груп залежностей.** Додали `pytest` — і або тягнете тестові інструменти в продакшн, або
   вручну ведете другий файл `requirements-dev.txt` і вічно стежите, щоб вони не розійшлися.
4. **`pip install -r` ніколи нічого не видаляє.** Приберіть рядок із файлу й запустіть знову — пакет
   залишиться встановленим.
5. **Не збирає й не публікує ваш проєкт.** Це просто файли в теці; немає нічого, що можна було б
   поставити командою `pip install statusboard`.

Пункт 4 перевіряється за п’ятнадцять секунд і зазвичай усіх дивує:

```bash
pip install rich
pip install -r requirements.txt     # rich у файлі немає
pip list | grep -i rich             # він досі тут
```

`poetry sync` і `uv sync` такий пакет приберуть (у Poetry 2.x це окрема команда; старий
`poetry install --sync` позначено застарілим). У pip аналога немає — хіба що видалити
venv і створити наново (що, чесно кажучи, цілком нормальна звичка).

## Конфлікт залежностей

Досі ми ставили пакети, які між собою дружать. Тепер подивимось, що буде, коли не дружать — і чому
саме в pip це найнебезпечніше.

У теці лежить окремий файл [`requirements-conflict.txt`](requirements-conflict.txt). **Справжній
`requirements.txt` він не змінює** — pip читає лише той файл, який ви назвали. Усередині два рядки:

```
flask==3.1.0
werkzeug==2.3.0
```

Flask 3.1.0 у своїх метаданих оголошує `Requires-Dist: Werkzeug>=3.1`. Ми ж поруч вимагаємо рівно
`2.3.0`. Такої комбінації не існує. Обмеження можна побачити на власні очі — воно лежить у
`METADATA` всередині wheel-а (`pip show flask` виводить лише **назви** залежностей, без версій):

```bash
pip download flask==3.1.0 --no-deps -d /tmp/fl
unzip -p /tmp/fl/flask-3.1.0-*.whl '*/METADATA' | grep Requires-Dist
# Requires-Dist: Werkzeug>=3.1
```

### Крок 1. Попросити pip це вирішити

`--dry-run` означає «порахуй, але не встановлюй» — ваш venv залишиться недоторканим:

```bash
pip install --dry-run -r requirements-conflict.txt
```

```
INFO: pip is looking at multiple versions of flask to determine which version is compatible...
ERROR: Cannot install -r requirements-conflict.txt (line 17) and werkzeug==2.3.0 because these
       package versions have conflicting dependencies.

The conflict is caused by:
    The user requested werkzeug==2.3.0
    flask 3.1.0 depends on Werkzeug>=3.1

ERROR: ResolutionImpossible
```

Код повернення — **1**. Це нормальна, здорова поведінка: pip порахував і відмовився.

### Крок 2. Те саме, але розв'язне

Закомментуйте `flask==3.1.0` і розкоментуйте рядок `flask` (без версії) — і той самий файл стане
розв'язним. Резолвер **відступить назад** і поставить `Flask 2.3.1` — найновіший реліз, який ще
приймає `Werkzeug 2.3.0`:

```bash
pip install --dry-run -r requirements-conflict.txt | grep -i "Would install"
# Would install ... Flask-2.3.1 ... Werkzeug-2.3.0 ...
```

Це і є резолюція залежностей: не «взяти найновіше», а **знайти набір версій, за якого виконуються всі
обмеження одночасно**. Poetry й uv у [`../03_poetry/`](../03_poetry/) та [`../04_uv/`](../04_uv/)
роблять на цьому файлі те саме й приходять до тієї ж `Flask 2.3.1` — різниця лише в швидкості й у
тексті помилки.

### Крок 3. Головне: pip може зламати вже готове оточення

Ось чого немає ні в Poetry, ні в uv. pip ставить пакети **по одному** й **не перевіряє те, що вже
встановлено**. Тому конфлікт, який у кроці 1 був чесною помилкою, тут просто відбувається:

```bash
python3 -m venv /tmp/broken-venv        # окремий venv, свій не чіпаємо
/tmp/broken-venv/bin/pip install flask==3.1.0
/tmp/broken-venv/bin/pip install werkzeug==2.3.0
```

Друга команда виводить `ERROR` — і **завершується з кодом 0**:

```
ERROR: pip's dependency resolver does not currently take into account all the packages that are
installed. This behaviour is the source of the following dependency conflicts.
flask 3.1.0 requires Werkzeug>=3.1, but you have werkzeug 2.3.0 which is incompatible.
```

Слово `ERROR`, код успіху, зламане оточення. У CI-скрипті, який перевіряє `if pip install; then`,
цей крок вважається успішним.

Наскільки зламане — видно не одразу, і це найгірше. Перевірте самі
файлом [`conflict_demo.py`](conflict_demo.py): він створює застосунок Flask з одним маршрутом, який
торкається сесії (тобто підписаної cookie — того, що робить кожна форма логіну).

```bash
/tmp/broken-venv/bin/pip install -q flask==3.1.0 werkzeug==2.3.0   # не потрібно, якщо вже зробили вище
/tmp/broken-venv/bin/python conflict_demo.py
```

```
flask     3.1.0
werkzeug  2.3.0

The session route raised:
...
    self.session_interface.save_session(self, ctx.session, response)
TypeError: Response.set_cookie() got an unexpected keyword argument 'partitioned'
```

Зверніть увагу, **що саме працює** в цьому зламаному оточенні: `import flask` проходить, застосунок
запускається, звичайний маршрут віддає 200. Ламається лише той шлях коду, який використовує API
нового Werkzeug. Тобто ви розгортаєте це на продакшн — і падає не збірка, а логін користувача.

Той самий скрипт у здоровому оточенні (де pip у кроці 2 сам підібрав `Flask 2.3.1`) друкує
`GET /login -> 200` і повертає 0.

### Що з цього виносимо

|                                                         | pip                                                                                                              |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Порахувати конфлікт наперед    | так,`--dry-run` (код 1)                                                                                  |
| Відступити до старішої версії | так, резолвер це вміє з 2020 року (pip 20.3)                                               |
| Захистити вже встановлене        | **ні** — послідовні `pip install` ламають оточення й повертають 0 |
| Знайти вже зламане                      | `pip check` (код 1) — але його треба **не забути запустити**            |

`pip check` — те, що варто додати в CI сьогодні ж:

```bash
/tmp/broken-venv/bin/pip check
# flask 3.1.0 has requirement Werkzeug>=3.1, but you have werkzeug 2.3.0.
```

Poetry й uv цієї проблеми не мають конструктивно: вони не «додають пакет», а **перераховують усе
оточення з lock-файлу**, тому непослідовного стану просто не буває. Як це виглядає — у
[`../03_poetry/`](../03_poetry/README.md#конфлікт-залежностей) і
[`../04_uv/`](../04_uv/README.md#конфлікт-залежностей).

Прибрати за собою:

```bash
rm -rf /tmp/broken-venv
```

## Частина 5. Як влаштований застосунок

### Маршрути

| Метод і шлях    | Функція     | Призначення                    |
| ------------------------- | ------------------ | ----------------------------------------- |
| `GET /`                 | `board`          | таблиця станів               |
| `GET /incidents`        | `incidents_page` | інциденти Cloudflare             |
| `POST /services`        | `add_service`    | додати сервіс із форми |
| `POST /services/delete` | `delete_service` | видалити сервіс             |

Дві важливі речі, які видно саме тут.

**Видалення — це POST, а не посилання.** GET за специфікацією має бути *безпечним* і повторюваним:
браузери роблять prefetch, пошукові роботи ходять за посиланнями, кнопка «назад» повторює запит.
Посилання `GET /services/delete?name=AWS` рано чи пізно видалить рядки, яких ніхто не просив видаляти.
Усе, що змінює стан на сервері, йде через POST.

**Post/Redirect/Get.** Обидва POST-и відповідають не HTML-ом, а редиректом на `/`. Без цього в адресному
рядку залишався б POST, і перезавантаження сторінки (або автооновлення раз на 30 секунд) повторно
відправило б форму й додало сервіс удруге.

### Шаблони і статика

Flask шукає поруч з `app.py` дві теки — за домовленістю, без жодних налаштувань:

- **`templates/`** — шаблони Jinja, які рендеряться на кожен запит. Підставляються значення, працюють
  `{% if %}` та `{% for %}`, і всі дані **автоматично екрануються** (захист від XSS).
- **`static/`** — файли, які віддаються браузеру як є. Ніякого рендерингу, ніякого Python. URL
  `/static/style.css` відповідає файлу на диску.

Стилі підключені через `url_for`, а не жорстко прописаним шляхом:

```html
<link rel="stylesheet" href="{{ url_for('static', filename='style.css') }}">
```

`url_for` просить Flask побудувати URL. Те саме в атрибутах `action` у формах: там вказано **ім’я
функції-обробника** (`url_for('add_service')`), а не шлях. Якщо маршрут перейменують — усе працюватиме.

### Успадкування шаблонів

`base.html` — спільний каркас: `<head>`, шапка, вкладки, підвал. Обидві сторінки роблять
`{% extends "base.html" %}` і заповнюють блоки:

| Блок                  | Для чого                                            |
| ------------------------- | ---------------------------------------------------------- |
| `title`                 | `<title>` сторінки                               |
| `heading`, `subtitle` | заголовок і підзаголовок             |
| `refresh`               | **порожній за замовчуванням** |
| `content`               | тіло сторінки                                  |
| `footer`                | підвал                                               |

Найцікавіший тут — `refresh`. Автооновлення потрібне **лише** дошці станів, тому
`<meta http-equiv="refresh" content="30">` лежить в `index.html`, а не в каркасі. Якби тег стояв у
`base.html`, сторінка інцидентів двічі на хвилину смикала б чуже API заради даних, які змінюються раз
на тиждень.

### Автооновлення без JavaScript

```html
<meta http-equiv="refresh" content="30">
```

Це вміння браузера, а не код сторінки. Браузер сам заводить таймер і через 30 секунд робить новий
`GET /`, ніби ви натиснули «оновити». На сторінці **немає жодного рядка JavaScript**.

Що варто знати, перш ніж використовувати це «по-справжньому»:

- це **повне перезавантаження**, тож позиція скролу й фокус клавіатури скидаються (а недописаний текст
  у формі — зникає);
- WCAG 2.2.1 вважає це проблемою доступності, якщо оновлення не можна поставити на паузу;
- кожні 30 секунд — це шість зовнішніх запитів **на кожну відкриту вкладку**.

### Обхід сервісів — послідовний

`check_all` — звичайний цикл:

```python
return [check(name, url, timeout) for name, url in services.items()]
```

Тому сторінка вантажиться приблизно стільки, скільки сума всіх перевірок (~1,4 с на шість сервісів).
Для шести це нормально, і простота важливіша за швидкість. Приблизно після двадцяти — вже ні, і тоді
з’являються потоки або `asyncio` (модуль 04).

### Обробка помилок у `checks.py`

Будь-яка мережева помилка перехоплюється й перетворюється на **рядок таблиці**, а не на виняток:

```python
except requests.RequestException as err:
    return {..., "error": type(err).__name__, "ok": False}
```

Логіка проста: сторінка станів, яка падає, коли впав відстежуваний сайт, падає рівно в той момент,
заради якого її й робили.

Ще одна деталь: `requests.get` **за замовчуванням іде за редиректами**. Саме тому Instagram, який
перекидає анонімних відвідувачів на сторінку входу, все одно показує 200.

> **Важливо:** обидві гілки `check()` повертають **однаковий набір ключів**, просто у випадку помилки
> `status` і `latency_ms` дорівнюють `None`. Словник, форма якого залежить від того, яка гілка його
> створила, — це `KeyError` через три файли.

### `services.py` — JSON замість бази даних

```python
SERVICES_FILE = Path(__file__).parent / "services.json"
```

Шлях прив’язаний до **файлу з кодом**, а не до робочої теки. `flask run` можна запустити звідки
завгодно, і простий `Path("services.json")` шукав би файл там, де випадково стоїть термінал. Помилка
підступна тим, що працює ідеально — рівно до того дня, коли застосунок запустять з іншої теки.

Обмеження такого «сховища», які варто назвати вголос:

- два одночасні записи → обидва читають файл, обидва змінюють свою копію, перемагає той, хто записав
  другим. Перша правка зникає без жодної помилки. Dev-сервер Flask багатопотоковий, тож це реальна
  гонка, а не теоретична;
- файл переписується цілком на кожну зміну;
- немає схеми — ніщо не заважає руками вписати число замість URL.

Для шести сервісів це прийнятно, для шести тисяч — ні. Звідси SQLite й SQLAlchemy в модулі 05.

## Частина 6. API Cloudflare

Сторінка статусу Cloudflare працює на **Atlassian Statuspage**, а той віддає публічний JSON API —
без ключа, без авторизації:

```
https://www.cloudflarestatus.com/api/v2/incidents.json
```

Перевірити можна прямо в терміналі:

```bash
curl -s https://www.cloudflarestatus.com/api/v2/incidents.json | python3 -m json.tool | head -40
```

Що варто знати:

- повертає **50 останніх** інцидентів — і це жорстке обмеження. Параметри `?page`, `?per_page`,
  `?limit` приймаються й **мовчки ігноруються**;
- Cloudflare відкриває 150–230 інцидентів на місяць, тож 50 — це приблизно три тижні. Це **вікно**, а
  не архів, і в підвалі сторінки так і написано;
- дати приходять в ISO-8601 із суфіксом `Z`: `2026-08-10T10:15:40.164Z`. Починаючи з Python 3.11
  `datetime.fromisoformat` читає такий рядок напряму, і результат одразу **з таймзоною** і одразу в UTC.

> Класична помилка на цьому місці — відрізати `Z` через зріз рядка. Тоді виходить naive datetime, який
> мовчки вдає, що він у локальному часі.

Глибший архів існує — `https://www.cloudflarestatus.com/history.json?page=N`, по три місяці на
сторінку, на роки назад. Але там бідніші записи, а поле `timestamp` приходить як **рядок з HTML**
усередині:

```
"Aug <var data-var='date'>10</var>, <var data-var='time'>10:15</var> ..."
```

Тому обрано чисті дані за три тижні, а не брудні за три роки.

### Сортування

API віддає інциденти за `created_at` — коли **завели запис**. На сторінці показується `started_at` —
коли інцидент **почався**. Ці два значення розходяться достатньо часто, щоб без власного сортування
дати в таблиці йшли явно не по порядку. Тому:

```python
incidents.sort(key=lambda incident: incident["started"], reverse=True)
```

Сортуємо за тим, що бачить читач.

### Помилка звернення до чужого API

`fetch()` **навмисно не ловить** мережеві помилки. Ловить їх маршрут:

```python
except requests.RequestException:
    return render_template("incidents.html", incidents=[], error=message, ...), 502
```

Дві причини:

1. Порожній список має означати «Cloudflare повідомив, що інцидентів немає». «Нічого не сталося» і
   «ми не змогли дізнатися» — різні відповіді, і зливати їх в один порожній список — це рівно те, як
   інструмент моніторингу починає заспокоювати вас під час аварії.
2. Код **502 Bad Gateway** обрано свідомо: сторінка відрендерилася чудово, а зламався запит, який
   *цей* сервер зробив до *іншого*. Саме це 502 і означає.

## Тести й dev-залежності

`pytest`, `bandit` і `ruff` потрібні тому, хто **пише** код, а не тому, хто його запускає. У pip немає
поняття груп залежностей, тому розділення доводиться робити **двома файлами руками**:

```bash
pip install -r requirements.txt -r requirements-dev.txt   # розробка
pip install -r requirements.txt                            # продакшн
```

```
requirements.txt        Flask, requests
requirements-dev.txt    pytest, bandit, ruff
```

Ніщо не заважає їм розійтися: додали пакет не в той файл — і дізнаєтесь про це на деплої. Poetry та uv
цю проблему прибирають одним маніфестом з іменованими групами.

### Запуск тестів

```bash
pytest              # 5 тестів, ~0.05 с
pytest -v           # з назвами
pytest -k delete    # лише ті, у назві яких є "delete"
pytest -x           # зупинитися на першій помилці
```

### Що саме перевіряється

Навмисно мінімальний набір — базовий CRUD через HTTP, два файли:

| Файл              | Про що                                                                                                           |
| --------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `tests/conftest.py` | одна фікстура`client`: тимчасовий `services.json` і Flask-клієнт без мережі |
| `tests/test_app.py` | read, create, create з порожнім полем, create з дублем, delete                                   |

Тести працюють на рівні HTTP — через `app.test_client()`, як це робив би браузер. Вони не знають про
`checks.py` чи `services.py`: перевіряється поведінка застосунку, а не його внутрішній устрій. Тому
код усередині можна переписати, і тести це переживуть.

**Жоден тест не виходить у мережу.** Це не побажання, а вимога: тест, який залежить від доступності
Instagram, падатиме через чужі проблеми й перестане що-небудь означати.

Два підміни в `conftest.py` роблять усю роботу. Перша — файл зі списком сервісів:

```python
monkeypatch.setattr(services, "SERVICES_FILE", tmp_path / "services.json")
```

Інакше тести переписали б справжній `services.json`.

Друга — та, на якій зазвичай спотикаються:

```python
monkeypatch.setattr(app_module, "check_all", ...)   # а не checks.check_all
```

`app.py` імпортує функцію через `from checks import check_all`, тож у просторі імен `app` лежить
**окреме посилання**. Підміна в модулі `checks` на нього вже не вплине.

### `bandit` — сканер безпеки

`ruff` шукає помилки стилю й логіки, `bandit` — **вразливості**. Він перевіряє код за базою типових
проблем: хардкоджені паролі, `shell=True`, слабка криптографія, запити без таймауту.

```bash
bandit -c bandit.yaml -r .          # перевірити проєкт
bandit -c bandit.yaml -r . -ll      # лише severity >= medium
bandit -c bandit.yaml -r . -f json  # для CI
```

На цьому коді bandit **не знаходить нічого** — і це не тому, що він нічого не вміє. Ось що він
повідомляє на навмисно поганому файлі:

```
[B602:subprocess_popen_with_shell_equals_true]  Severity: High
[B113:request_without_timeout]                  Severity: Medium
[B105:hardcoded_password_string]                Severity: Low
[B404:blacklist] Consider security implications of subprocess
```

`B113` тут особливо доречний: приберіть `timeout` з `requests.get` у [`checks.py`](checks.py) — і
bandit почне лаятися. Запит без таймауту може висіти вічно й підвісити весь застосунок.

Файл [`bandit.yaml`](bandit.yaml) потрібен, щоб виключити `.venv` і `tests`: `assert` у тестах —
це норма, але bandit позначає його як `B101`, бо в оптимізованому байткоді `assert` зникає.

### Демонстрація: що bandit насправді ловить

У теці [`bandit_demo/`](bandit_demo/) лежить файл [`insecure.py`](bandit_demo/insecure.py), написаний
**щоб його сканували, а не запускали**. Він виключений з `exclude_dirs`, тому звичайна перевірка
проєкту лишається чистою. Наведіть bandit на нього окремо:

```bash
bandit -r bandit_demo/
bandit -r bandit_demo/ -ll       # тільки medium і high
```

Результат — **33 знахідки, 29 різних правил**: 8 high, 11 medium, 14 low.

| Severity       | Правило     | Про що                                                                                                    |
| -------------- | ------------------ | -------------------------------------------------------------------------------------------------------------- |
| **High** | `B602`           | `subprocess(..., shell=True)` з інтерпольованим рядком — ін'єкція команд |
| **High** | `B501`           | `requests.get(..., verify=False)` — TLS без перевірки сертифіката                    |
| **High** | `B201`           | `app.run(debug=True)` — консоль Werkzeug відкрита в інтернет                        |
| **High** | `B301`           | `pickle.loads()` чужих байтів — це виконання чужого коду                    |
| Medium         | `B113`           | `requests.get()` без `timeout` — запит може висіти вічно                           |
| Medium         | `B608`           | SQL, зібраний форматуванням рядка                                                    |
| Medium         | `B506`           | `yaml.load()` замість `yaml.safe_load()`                                                            |
| Medium         | `B310`           | `urlopen()` без перевірки схеми — приймає і `file://`                            |
| Medium         | `B701`           | Jinja2 з`autoescape=False` — XSS                                                                           |
| Medium         | `B324`           | MD5 там, де потрібен SHA-256                                                                      |
| Low            | `B105`–`B107` | паролі й токени в коді                                                                       |
| Low            | `B108`           | передбачуваний шлях у`/tmp`                                                               |
| Low            | `B311`           | `random` замість `secrets` для токенів                                                    |
| Low            | `B110`           | `except Exception: pass`                                                                                     |

Файл побудований парами: поруч із небезпечною функцією стоїть безпечний варіант — `fingerprint` і
`fingerprint_safely`, `find_user` і `find_user_safely`, `list_dir` і `list_dir_safely`. Так видно не
лише що зламано, а й як лагодити.

Дві деталі, які добре обговорити на занятті:

- **`B110` не спрацьовує на `except OSError: pass`** — лише на широкому `except Exception`. Ловити
  конкретну помилку, яку ви свідомо ігноруєте, — нормально; ховати всі підряд — ні.
- **Команди в демо нешкідливі** (`echo`, `ls`). Bandit позначає **патерн**, а не корисне
  навантаження, тож навчальному файлу не потрібна руйнівна команда, щоб продемонструвати проблему.

> ⚠ Цей файл не можна запускати й не можна нічого з нього копіювати. Він існує рівно для того, щоб
> показати звіт сканера.

## pre-commit — запускати ruff і bandit автоматично

`pre-commit` вішає перевірки на git-хук: вони спрацьовують на `git commit` і **лише для тих файлів,
що ви застейджили**. Конфігурація — [`.pre-commit-config.yaml`](.pre-commit-config.yaml).

```bash
pre-commit install          # вписати хук у .git/hooks (один раз)
pre-commit run --all-files  # прогнати зараз по всьому
pre-commit autoupdate       # підняти версії в rev:
pre-commit run ruff-check   # тільки один хук
```

Три хуки: `ruff-check` (шукає проблеми й виправляє), `ruff-format` (форматує), `bandit` (безпека).

### Три деталі, які варто знати

**1. Хуки ставляться на весь git-репозиторій, а не на теку.** У цьому репозиторії лежить кілька
проєктів, тому `.pre-commit-config.yaml` тут містить фільтр:

```yaml
files: ^module01/02_pipenv/
exclude: ^module01/02_pipenv/(bandit_demo|\.venv)/
```

Без нього хуки з цієї теки перевіряли б і дві інші копії того самого застосунку. З кореня репозиторію
конфіг треба вказувати явно:

```bash
pre-commit run --config module01/02_pipenv/.pre-commit-config.yaml --all-files
```

**2. `--exit-non-zero-on-fix` — не косметика.** З простим `--fix` ruff виправляє файл і завершується
кодом 0. Хук рапортує `Passed`, коміт проходить, а ваш код мовчки переписали. Перевірено: з голим
`--fix` зламаний файл давав `Passed`, з прапорцем — `Failed`.

**3. `--all-files` означає «усі файли, які знає git».** Поки тека не додана в git, хуки покажуть
`(no files to check) Skipped`. Це не поломка конфігурації — просто `git add` ще не робили.

### Що хуки реально ловлять

Перевірено на навмисно зіпсованому коді:

```python
def broken():
    msg = f"no placeholders"          # ruff: F541
    return os.system("echo " + msg)   # bandit: B605
```

```
ruff check....................Failed
bandit........................Failed
>> Issue: [B605:start_process_with_a_shell] Starting a process with a shell
```

`bandit_demo/` виключено з хуків навмисно: `ruff --fix` полагодив би саме те, що там має лишатися
зламаним.

## Типові граблі

| Симптом                                              | Причина                                                                                                      |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `ModuleNotFoundError: No module named 'flask'`            | venv не активований, або пакети поставлені в інший інтерпретатор |
| `error: externally-managed-environment`                   | ставите в системний Python — потрібен venv                                                |
| `TemplateNotFound: index.html`                            | тека`templates/` не поруч із `app.py`                                                              |
| Змінили CSS, а нічого не змінилося | кеш браузера — Ctrl+Shift+R                                                                             |
| Форма додає сервіс двічі               | забули редирект після POST                                                                       |
| Файл`services.json` не знаходиться       | шлях відносний до робочої теки, а не до`__file__`                                  |
| У шаблоні виводиться слово`None`   | немає перевірки`is not none` для необов’язкових полів                         |

## Вправи

1. Додайте через форму `https://httpbin.org/status/500` і подивіться, чим 5xx відрізняється від
   недосяжного хоста: один **відповів**, інший **не з’єднався**. Це різні речі.
2. `check_all` приймає `timeout`, але його ніхто не задає ззовні. Звідки мало б братися це значення?
   (Відповідь — у `03_poetry` і в темі конфігурації.)
3. Зламайте застосунок навмисно: `pip uninstall requests`, перезавантажте сторінку, прочитайте
   traceback. Потім `pip install -r requirements.txt`. Саме так виглядає забута залежність у продакшні.
4. Автооновлення стирає недописане в формі. Полагодьте це **без JavaScript**. (Підказка: тег `<meta>`
   рендерить сервер — отже, сервер може вирішити його не рендерити. Але на якій підставі, якщо HTTP не
   має стану?)
5. Поверніть JSON-ендпойнт: `GET /api/status`, який віддає ті самі дані й **код 503**, щойно щось
   недоступне. Подумайте, чому вердикт варто класти саме в код відповіді, а не тільки в тіло.
